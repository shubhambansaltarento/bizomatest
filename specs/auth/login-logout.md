## Purpose

A Bizom user signs in with a username and password to reach the application, and signs out from the user menu. Login and logout are the entry and exit point for every other module, so they are also exposed as a shared fixture (`authedPage`) that every module spec reuses.

## Preconditions & test data

- An active user exists: `BIZOM_USERNAME` / `BIZOM_PASSWORD` from `.env`.
- Invalid credentials used by negative tests are generated by the test and never exist in the system.
- Each test starts with a fresh browser context (no cookies, no session).
- Company settings that change login behaviour, as read on dev (Settings → All Settings, `/settings/allsettings`, 11 Nov 2026). The tests don't change them: they are company-wide on a shared server.

| Setting                        | Value on dev | What it does (app's description) |
| ------------------------------ | ------------ | -------------------------------- |
| `google_signin`                | **1**        | Shows Google sign-in |
| `microsoft_signin`             | 0            | Microsoft sign-in (1), or Microsoft SAML SSO (2) |
| `passwordresetlock`            | 0            | Blocks a password reset for 24 hours after a password change |
| `initialPasswordReset`         | 0            | Asks the user to reset their password on first login |
| `forceLogoutOnPasswordChange`  | 0            | Logs the user out when their password is changed |
| `changepasswordnotification`   | `{"enable": 0,"alert_days": [14,7,5,3,1]}` | Alerts on login, n days before the password expires |
| `password_ageing_days`         | not read     | Forces a password reset after n days (0 = off) |
| `requiredPasswordLoginMinutes` | 0            | "Used in APP only": asks for the password again after n minutes |
| `twofactorauth`                | 0            | 0 none, 1 SMS, 2 email, 3 both, 4 authenticator app (TOTP) |
| `attendanceimage`              | 0            | Requires a photo when marking attendance |

## Acceptance criteria

### AUTH-01 Valid user can log in

- **Given** I am on the login page
- **When** I enter a valid username and password and click **Login**
- **Then** I land on `/users/ajaxuserindex`
- **And** the "Welcome" banner and the user icon are visible

### AUTH-02 Logged-in user can log out

- **Given** I am logged in
- **When** I open the user menu and click **Logout**
- **Then** I am on `/users/login`
- **And** the username and password fields are visible

### AUTH-03 Wrong password is rejected

- **Given** I am on the login page
- **When** I enter a valid username with a wrong password and click **Login**
- **Then** I stay on `/users/login`
- **And** the message "Invalid User credentials" is shown in the error banner (since Oct 2026 it is also repeated under the form)

### AUTH-04 Unknown username is rejected

- **Given** I am on the login page
- **When** I enter a username that does not exist and click **Login**
- **Then** I stay on `/users/login`
- **And** the message "Invalid username or password." is shown

> **Observation:** this message differs from AUTH-03, which reveals whether a username exists (user enumeration). Raised for the product team to decide; the spec records current behaviour.

### AUTH-05 Empty form does not log in

- **Given** I am on the login page
- **When** I click **Login** without entering a username or password
- **Then** I stay on `/users/login` and am not logged in

### AUTH-06 Protected page requires login

- **Given** I am not logged in
- **When** I open `/users/ajaxuserindex` directly
- **Then** I am redirected to `/users/login`

> **Changed (22 Oct 2026):** until 20 Oct the app redirected to `/users/login?redirect=%2Fusers%2Fajaxuserindex`, keeping the page the user asked for. Since the Bootstrap 5 update the `redirect` parameter is gone. Raised for product confirmation; if it should come back, restore the stricter check in the test.

### AUTH-07 Session ends on logout

- **Given** I logged in and then logged out
- **When** I press the browser Back button, or open `/users/ajaxuserindex` directly
- **Then** I am on the login page, not back inside the app

### AUTH-08 Logged-in user opening the login page goes to the dashboard

- **Given** I am logged in
- **When** I open `/users/login`
- **Then** I am redirected to `/users/dashboard`

### AUTH-09 Spaces around the username are ignored

From the team sheet, row 2. Checked on dev on 11 Nov 2026: it logs in.

- **Given** I am on the login page
- **When** I enter a valid username with spaces after it, the right password, and click **Login**
- **Then** I land on `/users/ajaxuserindex`, logged in as that user
- **And** the same happens with spaces before the username, and with spaces on both sides

### AUTH-10 Spaces around the password are ignored

From the team sheet, row 4. Checked on dev on 11 Nov 2026: it logs in.

- **Given** I am on the login page
- **When** I enter a valid username and the right password with spaces before and after it, and click **Login**
- **Then** I land on `/users/ajaxuserindex`, logged in as that user

> **Question for product:** trimming the password means a password can't start or end with a space, and `" secret "` logs in as `"secret"`. The sheet expects this; confirm it is intended.

### AUTH-11 Login page offers Google sign-in

From the team sheet, row 20. The web part only: the sheet's case is for the mobile app (Bizom Next).

- **Given** `google_signin` is 1 and `microsoft_signin` is 0 (as on dev)
- **When** I open the login page
- **Then** "OR" and a Google sign-in button are shown below **Login**
- **And** the button links to Google's sign-in (`accounts.google.com/o/oauth2/auth`, `response_type=code`)
- **And** no Microsoft sign-in button is shown

> The test does not click through to Google: signing in with a real Google account can't be automated reliably (Google blocks automated browsers and asks for 2FA). Note that the link's `redirect_uri` is `devlogin.bizomdev.in/users/login`, not this server.

## Shared behaviour for other modules

Every module spec uses the `authedPage` fixture from `fixtures/auth.fixture.ts`:

- Before the test: performs AUTH-01 and verifies it.
- After the test: performs AUTH-02 and verifies it.

Module specs do not repeat these steps or their criteria.

## Out of scope

- reCAPTCHA (the dev environment does not block automated logins; if it starts enforcing, these tests will fail at login).
- Login throttling. After a burst of roughly 30 logins in 30 seconds, the dev server temporarily rejects every login, valid or invalid, by redirecting back to `/users/login` with no message. Normal runs stay well below this; repeated stress runs (`--repeat-each`) can trip it.
- Forgot / change password, account lockout after repeated failures.
- Completing a Google or Microsoft sign-in (see AUTH-11).
- The sheet's setting-dependent cases (`specs/config/login-settings.md`) and the mobile app cases (`docs/mobile-login-test-cases.xlsx`).
- Honouring the `redirect` parameter after login (the default landing page is the same URL, so this can't be verified with the current data).
